# 128、4K、32K 到底在说什么

这组数字的单位通常是 **token**，不是汉字数、英文单词数、字节数，也不是并发数。Token 是模型分词器切分文本后的最小计数单位；同一句话换一个模型或 tokenizer，token 数可能不同。

## 先看一个最小例子

测试名称里的 `128/64` 通常表示：

- 输入（Prompt）长度为 128 tokens。
- 最多生成 64 tokens。
- 一次请求最多占用 `128 + 64 = 192 tokens` 的上下文。

对应的请求大致如下：

```json
{
  "model": "your-model",
  "prompt": "一段经过 tokenizer 计算后为 128 tokens 的文本",
  "max_tokens": 64,
  "temperature": 0
}
```

这里的 `64` 是输出上限，不保证一定生成 64 tokens。模型遇到 EOS 时可能提前结束；性能压测通常使用 `ignore_eos`，尽量得到固定长度输出。

`4096/128` 同理：输入 4,096 tokens，最多输出 128 tokens，总预算是 4,224 tokens。它描述的是这次请求的形状，不代表服务只能支持 4K。

## 32K、64K、128K 是服务的总窗口

在这套测试中，`K` 按 1,024 计算：

| 简写 | 精确 token 数 | 可以怎样理解 |
|---|---:|---|
| 4K | 4,096 | 一次中等长度的 Prompt |
| 32K | 32,768 | 输入与输出合计最多 32,768 tokens |
| 64K | 65,536 | 输入与输出合计最多 65,536 tokens |
| 128K | 131,072 | 输入与输出合计最多 131,072 tokens |

必须满足下面的关系：

```text
输入 tokens + 最大输出 tokens <= 服务的 max context
```

所以三档边界用例写成：

| 用例名 | 输入 | 输出 | 算式 | 需要的服务配置 |
|---|---:|---:|---:|---:|
| `ctx-31k-1k-c1` | 31,744 | 1,024 | 31,744 + 1,024 = 32,768 | 32K |
| `ctx-63k-1k-c1` | 64,512 | 1,024 | 64,512 + 1,024 = 65,536 | 64K |
| `ctx-127k-1k-c1` | 130,048 | 1,024 | 130,048 + 1,024 = 131,072 | 128K |

这里把 1K 留给输出，因此输入分别叫 31K、63K、127K，而不是直接塞入 32K、64K、128K。比如在 32K 服务里请求“32K 输入 + 1K 输出”，总数会变成 33K，服务应当拒绝它。

## 把它想成一张固定大小的桌子

可以把上下文窗口想成一张桌子：Prompt 和模型即将生成的内容都必须放在桌面上。

```text
32K 桌面：[ 31K 输入 ][ 1K 输出 ]
64K 桌面：[             63K 输入             ][ 1K 输出 ]
128K桌面：[                         127K 输入                         ][ 1K 输出 ]
```

桌面越大，模型能读取的历史、文档或代码越多，但不代表请求免费变快。输入越长，Prefill 工作越多，通常首先表现为 TTFT（首 token 延迟）增长；固定输出 1K 时，TPOT（后续每 token 时间）往往不会按输入长度同比增长。

## 这些数字和文字长度怎样换算

不要用固定比例把 token 换成汉字或单词。只能做很粗略的直觉估计：英文常见文本经常约为 1 token 对应 0.75 个单词；中文可能一个汉字占一个或多个 tokens，也可能把常见词组合并为一个 token。代码、数字、空格和特殊符号又会改变比例。

需要精确长度时，必须使用与服务相同的 tokenizer：

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("/path/to/model")
text = "这是要发送给模型的实际文本。"
print(len(tokenizer.encode(text, add_special_tokens=False)))
```

Chat API 还会加入 system/user/assistant 标记，因此“正文的 token 数”不一定等于服务最终报告的 `prompt_tokens`。本套件的边界性能测试使用 `/v1/completions`，就是为了避免 Chat Template 让长度超出窗口。

## 最容易混淆的三个概念

- `input_tokens` / `output_tokens`：一条请求有多长。
- `max_context`：输入和最大输出加起来能有多长。
- `C=1`、`C=2`：同时在途的请求数；它是并发，不是 token 长度。

例如 `127K+1K C=1` 表示单次只有一个请求在跑，每条请求输入 130,048 tokens、最多输出 1,024 tokens；它不是 1 个 token，也不是每秒 1 个请求。
