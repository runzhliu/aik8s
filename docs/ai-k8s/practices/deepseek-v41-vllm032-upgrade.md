# vLLM 0.32.0 升级实测：DeepSeek-V4.1-Flash 在八卡 H20-3e 上快了多少

DeepSeek-V4.1-Flash 是采用混合专家与 Engram 条件记忆的开放权重多模态模型。此前的[八卡部署文章](deepseek-v41-flash-h20-day0.md)使用模型发布时的固定支持构建。本次保持原版模型权重，比较那个构建与 vLLM 0.32.0，回答一个实际运维问题：看过新版性能提升的讨论之后，现有 H20-3e 服务是否值得升级？

本轮同机串行完成 **60 轮、1,968 个正式请求**。8K 输入、并发 8 的输出吞吐提高约 **123%**，单并发长输出基本持平；旧版和新版分别有 **6/984、11/984** 个请求未返回有效文本。新版的收益主要出现在长输入和较高并发，完整输出检查仍是升级验收的一部分。

## 1. 为什么做这次升级实验

最近围绕 vLLM 新版的公众号和公开文章讨论很多，这次实验从这些讨论出发，技术依据回到原始资料。vLLM 团队在 **2026 年 10 月 7 日**的官方文章中报告了 AgentX 场景的显著提升，摘要给出低并发 1.9 倍、150 TPS 约束下吞吐 5.3 倍的结果。这篇文章早于 0.32.0 发布，比较的是其特定优化配置与官方 Day 0 实现，不能理解成任何机器升级到 0.32.0 都能获得同样倍数。[官方性能文章](https://vllm.ai/blog/2026-10-07-deepseek-v41-flash)

**0.32.0 于 10 月 18 日发布**，发布说明包含 Hopper/SM90 优先选择 Humming 的默认变化，并锁定 `humming-kernels==0.1.17`。[0.32.0 Release](https://github.com/vllm-project/vllm/releases/tag/v0.32.0)

因此实验不做“最新版与任意旧版”的比较，而是恢复此前文章的具体镜像，再换成固定 0.32.0 镜像。没有使用滚动 nightly，也没有更换为 `DeepSeek-V4.1-Flash-1017`。

### 相同命令不等于相同执行路径

两版使用以下相同的显式启动参数，`/model` 代表挂载后的模型目录：

```bash
vllm serve /model \
  --served-model-name deepseek-v41-flash \
  --tensor-parallel-size 8 \
  --enable-expert-parallel \
  --max-model-len 32768 \
  --max-num-seqs 32 \
  --max-num-batched-tokens 8192 \
  --gpu-memory-utilization 0.85 \
  --tokenizer-mode deepseek_v41 \
  --reasoning-parser deepseek_v41 \
  --tool-call-parser deepseek_v41 \
  --enable-auto-tool-choice \
  --engram-config '{"cpu_offload":false}' \
  --no-enable-prefix-caching \
  --host 0.0.0.0 --port 30000
```

检查实际日志后，发现新版默认启用了 **SWA bounded replay**，即滑动窗口注意力的有界重放。旧构建源码中没有 `swa_bounded_replay` 配置项；新版日志明确说明，eager Prefill 中第 20 层为全部 Token 写入 KV，其余相关计算与第 21–39 层只处理每个请求末尾 128 个 Token。关闭前缀缓存并不会自动关闭这条 decoder 优化路径。

新版还实际记录了 `HummingMxfp8LinearKernel` 与 `HummingGroupedExperts` 的选择。因此，这次测量的是**镜像、依赖和默认执行策略一起升级后的效果**，不能把某个提升百分比全部归给 Humming。若要分离 SWA bounded replay 的贡献，需要另做开关对照；这不在本轮两组实验中。官方也说明 bounded replay 并非逐位精确重算，性能收益之外仍需业务质量回归。[有界重放的实现说明](https://vllm.ai/blog/2026-10-07-deepseek-v41-flash)

## 3. 怎么测，失败怎么计算

本轮包含 10 个“输入长度×输出长度×并发”场景，每个版本各做 3 轮正式测量。C1、C8、C32 每轮分别发 8、16、64 个请求，场景预热单列。所有正式请求的输入指纹逐轮配对一致。

输出吞吐来自成功返回的输出 Token 数除以该轮测量时间。TTFT 为 Time to First Token，本文客户端具体测量首段非空文本的等待；TPOT 为 Time per Output Token；E2E 为端到端耗时。表格先在每轮计算 P95，再取三轮中位数，不是把所有请求拼起来计算一次 P95。

成功条件包括 HTTP 200、流式结束标志、非空文本、有效 usage 及指定输出长度。**失败保留在原请求分母中**；含失败的场景仍列出观测吞吐，但不进入无失败场景的升级收益图。

空文本失败没有有效的首内容延迟，因此延迟分位数只覆盖有效响应；失败数与原请求分母另外展示。吞吐保留该轮完整测量时间，不因失败删掉一段耗时。

首批执行曾因编排器把预热错误算入正式失败保护，提前停止部分新版场景。补测修复计数逻辑后，每个场景独立完成三轮。原节点已经被其他任务使用，因此本轮两版均在另一台同规格节点重新配对，不把不同节点的轮次拼成一个中位数。阶段超时、服务失联、CUDA/NCCL/OOM 与跨节点独立看护负责终止和清理；编排成功与请求成功分别统计。

## 4. 吞吐：长输入收益明显，单并发长输出接近持平

![不同负载的升级收益；仅使用两版全部请求成功的场景](../../assets/practices/deepseek-v41-vllm032-upgrade/v3/throughput.png)

| 8,192→128 / C8 | 97.69 | 217.46 | +122.6% | 48/48 | 48/48 |
| 8,192→128 / C32 | 106.52† | 263.14† | — | 190/192 | 190/192 |
| 1,024→512 / C1 | 115.00 | 113.69 | −1.1% | 24/24 | 24/24 |
| 1,024→512 / C8 | 609.73 | 676.93 | +11.0% | 48/48 | 48/48 |
| 1,024→512 / C32 | 1,222.29 | 1,576.39† | — | 192/192 | 190/192 |
| 24,576→128 / C1 | 27.74† | 52.25† | — | 23/24 | 23/24 |
| 24,576→128 / C8 | 35.10 | 87.57† | — | 48/48 | 47/48 |
| 24,576→128 / C32 | 35.78† | 94.78† | — | 190/192 | 189/192 |

8K/C8 的新版吞吐为原来的 **2.23 倍**，对应“提高 122.6%”，不是“提高 2.23 倍”。相反，1K→512/C1 从 115.00 变为 113.69 Token/s，约下降 1.1%；三个短时重复不足以把这个小差异认定为稳定回退。

固定长度请求的吞吐同时受 Prefill 等待与 Decode 速度影响。新版更快地处理长输入，能减少首内容等待，也能更快把后续请求送进解码；这不意味着每个请求生成下一个 Token 都按同样比例变快。

## 5. 速度提高了，为什么还有失败

| 本轮正式统计 | 原文构建 | 0.32.0 |
| --- | ---: | ---: |
| 执行轮数 | 30/30 | 30/30 |
| 全部请求成功的轮数 | 25 | 21 |
| 包含失败请求的轮数 | 5 | 9 |
| 成功请求 | 978/984 | 973/984 |
| 失败请求 | 6/984，0.61% | 11/984，1.12% |

这 17 个失败请求都返回了 HTTP 200、`[DONE]` 和正数 `completion_tokens`，但所有 `choices[].text` 始终为空。比如一条失败流的关键字段如下，已省略 ID 和时间戳：

```text
HTTP 200
data: {"choices":[{"text":""}]}
...
data: {"usage":{"prompt_tokens":1024,"completion_tokens":128,"total_tokens":1152}}
data: [DONE]
```

![空文本响应的检查路径与两版失败请求分母](../../assets/practices/deepseek-v41-vllm032-upgrade/v3/response-validation.png)

因此，`vllm bench` 子进程退出码为 0、服务健康检查成功，都不足以证明这轮业务输出成功。严格客户端将这些请求判失败，没有把 usage 中的 128 或 512 个 Token 直接当成用户收到的有效文本。

两版均能出现该现象。目前证据定位到合成固定长度 Prompt 的生成、特殊 Token、解码与流式输出这条路径，尚未分离根因；不能据此认定 GPU 崩溃、Humming 错误或单一版本回归。0.61% 与 1.12% 也是本轮合成负载的观察比例，不是生产故障率或统计显著性结论。

进一步排查应固定失败输入，保留 token IDs，比较非流式与流式、Token 解码前后，以及自然语言 Prompt 对照；再分别切换相关优化。不要同时换模型、Prompt 和采样参数后用一次成功覆盖原失败。

首批开放到达率 0.300 req/s 的三轮也出现失败请求，触发保护；0.480 和 0.660 两档保留为未执行，没有据此给出 SLO 容量上限。SLO 为 Service Level Objective，服务等级目标；本轮主要回答版本对比，不提供正式生产容量承诺。

## 7. 功能检查与无人值守过程中学到的事

本轮两版的基础文本与完整流硬门槛、工具调用解析、单图蔬菜识别及交换顺序的双图样例均通过。视觉使用原始 2,048 Token 预算，新版没有触发额外 4,096 Token 诊断。首批新版曾在一条双图顺序问题中耗尽推理预算，本轮通过说明它能完成这些样例，不能把一次通过当作多模态准确率评测。

无人值守的关键是分清失败层级。预热失败不计入正式连续失败计数；一个输入长度与并发场景失败，不阻止其他健康场景继续运行；服务失联或 GPU 运行时故障才终止整组。正式失败保留分母、代码哈希和原始流，诊断单独编号。阶段期限和独立看护负责资源清理，最终仍要逐项审核实验成绩。

本轮没有执行 1M 上下文、CPU Engram、DSpark、长期稳定性或质量基准，也没有把本机的短时结果换算为线上每卡业务容量。测试材料和原始环境配置保留在私有目录；公开的[逐轮脱敏结果](../../assets/practices/deepseek-v41-vllm032-upgrade/results.json)包含全部 60 轮的分母、失败数、吞吐、延迟及源文件哈希。

## 8. 怎么决定是否升级

对 **8K 以上输入、检索增强生成或 Agent 历史较长**的服务，0.32.0 值得安排灰度。优先观察真实业务的首内容等待、排队、有效输出比例，以及代表性任务质量。长输入收益明显，但 bounded replay 的默认变化需要作为质量回归条件记录。

对 **单用户、短输入、长时间连续生成**的服务，不应预期升级后 Decode 速度翻倍。本轮 1K→512/C1 接近持平，目标如果是降低逐 Token 延迟，应单独测试对应模式。

对 **高并发服务**，先解决空输出定位与验收，再增加压力。升级时固定镜像 Digest、模型快照与依赖清单，保留旧镜像和回滚路径；容量结论应基于真实 Prompt、错误预算和延迟目标重新建立。

这次实测给出的判断是：0.32.0 在这套八卡 H20-3e 配置上确有明显的长输入收益，收益分布与请求形状有关；同时，完整流校验暴露的问题依然需要在上线前定位。
